## 1. 本周最终目标

第二周完成后，项目应具备以下能力：

1. 可以通过 Uvicorn 启动 FastAPI 应用。
2. 提供 `/health` 健康检查和 Swagger/OpenAPI 文档。
3. 使用 Pydantic 定义 HTTP 请求和响应结构。
4. 使用 PostgreSQL 保存文档元数据，不再由 API 使用 JSON 文件保存元数据。
5. 使用 SQLAlchemy 建立数据库模型、Session 和数据访问层。
6. 使用 Alembic 从空数据库创建表，并完成至少第二次结构迁移。
7. 提供文档上传、列表、详情、修改和删除 API。
8. 对主要成功和失败场景进行自动化测试。
9. 保留第一周 CLI 版本和原有测试，不让新功能破坏旧功能。
10. 形成代码、学习文档、数据库设计和演示记录。

### 本周目标调用链

```text
HTTP 请求
  → FastAPI Router
  → Pydantic 请求校验
  → DocumentService
  → SQLAlchemy Repository
  → PostgreSQL
  → Pydantic 响应序列化
  → HTTP JSON 响应
```

文件本体与元数据仍分开保存：

```text
文件本体  → data/uploads
文档元数据 → PostgreSQL
```

## 4. 模型分工说明

第二周会同时出现多种“模型”，它们不是互相替换，而是分别处理不同边界。

| 模型 | 建议名称 | 技术 | 职责 |
| --- | --- | --- | --- |
| 领域模型 | `Document` | Python dataclass | Service 内部使用的业务对象 |
| JSON 数据结构 | `DocumentData` | TypedDict | 第一周 JSON Repository 的字典类型 |
| API 请求模型 | `DocumentUpdateRequest` 等 | Pydantic | 校验客户端传入的 HTTP 数据 |
| API 响应模型 | `DocumentResponse` | Pydantic | 控制 HTTP 返回字段并生成 OpenAPI |
| 数据库模型 | `DocumentORM` | SQLAlchemy | 定义 PostgreSQL 表、字段和约束 |

推荐数据流：

```text
客户端 JSON / 文件
  → Pydantic API Schema
  → Document 领域对象
  → DocumentORM
  → PostgreSQL
```

查询返回时方向相反：

```text
PostgreSQL
  → DocumentORM
  → Document 领域对象
  → DocumentResponse
  → HTTP JSON
```

本周不直接删除 `DocumentData`，因为第一周的 JSON Repository 和测试仍需保留。等数据库版本稳定并完成阶段验收后，再决定 JSON Repository 是保留为示例还是停止在主程序中使用。

## 12. 阶段 6：文档 CRUD API 集成

### 阶段目标

将 FastAPI、Pydantic、Service、SQLAlchemy Repository 和 PostgreSQL 串成完整 HTTP 调用链。

### 目标接口

| 方法 | 路径 | 功能 | 成功状态码 |
| --- | --- | --- | --- |
| `POST` | `/api/v1/documents` | 上传并创建文档 | `201` |
| `GET` | `/api/v1/documents` | 分页查询文档列表 | `200` |
| `GET` | `/api/v1/documents/{id}` | 查询文档详情 | `200` |
| `PATCH` | `/api/v1/documents/{id}` | 修改允许更新的元数据 | `200` |
| `DELETE` | `/api/v1/documents/{id}` | 删除文档及文件副本 | `204` |

### 关于上传接口

HTTP 客户端不能直接向服务器传入 `D:\...` 这样的本地路径。创建文档应使用 `multipart/form-data` 上传文件：

```text
客户端文件
  → FastAPI UploadFile
  → 限制文件名和大小
  → 写入 uploads
  → 保存 PostgreSQL 元数据
```

届时需要安装文件上传依赖，但不在阶段 2 提前引入。

### 更新范围

第一版本建议只允许修改：

```text
name
status（如业务上确有需要）
```

不允许客户端修改：

```text
id
original_path
stored_path
file_size
created_at
```

### 异常与状态码

| 场景 | 状态码 |
| --- | ---: |
| 参数或请求体校验失败 | `422` |
| 文档不存在 | `404` |
| 文件类型或大小不允许 | `400` |
| 重复或冲突 | `409` |
| 创建成功 | `201` |
| 删除成功且无响应体 | `204` |
| 未处理的服务器错误 | `500` |

### 一致性重点

添加文件时：

```text
文件保存成功 + 数据库提交成功 → 整体成功
数据库提交失败 → 清理已保存文件
```

删除文件时需要明确顺序和失败处理，避免出现数据库记录与文件副本不一致。
