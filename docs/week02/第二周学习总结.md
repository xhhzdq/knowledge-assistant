### 2.5 分层与依赖关系

当前主要调用链为：

```text
HTTP 请求
  → FastAPI Router
  → Depends(get_document_service)
  → DocumentService
  → DocumentRepository Protocol
  → SqlAlchemyDocumentRepository
  → SQLAlchemy Session
  → PostgreSQL
```

主要分工：

| 层 | 主要职责 |
| --- | --- |
| Router | 接收 HTTP 参数、选择状态码、把领域异常转换为 HTTP 错误 |
| Pydantic Schema | 校验和描述 HTTP 输入输出 |
| Service | 文件操作、业务规则及文件与元数据的一致性 |
| Repository | 隔离数据访问细节 |
| SQLAlchemy ORM | Python 对象与数据库表之间的映射 |
| Session | 工作单元、事务边界和数据库交互 |
| Alembic | 数据库表结构的版本管理 |

## 3. 一个重要问题：为什么空名称是 422

更新请求中的名称定义了：

```python
name: str | None = Field(default=None, min_length=1, max_length=255)
```

当请求发送 `{"name": ""}` 时，空字符串不满足 `min_length=1`。请求还没有进入 `update_document()` 路由函数，就已经被 FastAPI/Pydantic 拒绝，因此响应是 `422 Unprocessable Content`。

Service 中仍然保留 `strip()` 后判空的业务保护。例如名称只包含空格时，字符串长度可以通过 Pydantic，但去除空格后为空，此时 Service 抛出 `InvalidDocumentError`，路由返回 `400 Bad Request`。

这说明两层校验不是重复：

- Pydantic 保护 HTTP 边界和数据形状。
- Service 保护业务规则，并保证 CLI、API 或未来其他入口调用它时规则一致。

## 4. 数据存储现状

项目目前有两条可以共存的入口：

| 入口 | Repository | 元数据位置 | 文件位置 |
| --- | --- | --- | --- |
| 第一周 CLI | `JsonDocumentRepository` | `data/documents.json` | `data/uploads` |
| 第二周 API | `SqlAlchemyDocumentRepository` | PostgreSQL `documents` 表 | 配置的 uploads 目录 |

两条入口复用领域对象和 Service，但默认数据源不同。因此用 CLI 添加的记录不会自动出现在 API 列表中，反之亦然。
