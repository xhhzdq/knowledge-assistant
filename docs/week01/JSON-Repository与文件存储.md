# JSON Repository 与文件存储

## 1. 数据目录职责

```text
data/
├── documents.json  # 文档元数据，由程序自动创建
└── uploads/        # 被管理文件的副本
```

`docs/week01` 保存学习文档，`data` 保存程序运行数据，两者不能混用。运行数据已经配置在 `.gitignore` 中，避免把用户上传文件提交到 Git。

## 2. 为什么分开保存

文件本体可能是 PDF、图片或文本，适合直接保存在文件系统；ID、状态、路径和创建时间等结构化信息适合保存在 JSON。后续可以把 JSON Repository 替换为 SQLAlchemy Repository，而 Service 的业务流程保持相对稳定。

## 3. Repository 职责

`JsonDocumentRepository` 只负责元数据：

- `list_all`：读取全部文档元数据。
- `get_by_id`：按 ID 查询。
- `add`：增加文档并写入 JSON。
- `delete`：删除文档元数据。

Repository 不复制上传文件，也不负责命令行输出。

## 4. Service 职责

`DocumentService` 组织一次完整业务操作：

```text
验证源路径
  → 创建 uploads 目录
  → 为存储文件生成唯一名称
  → 读取文件大小
  → 复制文件本体
  → 保存 Document 元数据
```

添加失败时会清理已经复制的文件，避免出现只有文件、没有元数据的孤立数据。

删除前会确认目标处于 `uploads` 目录内，防止损坏的元数据导致程序删除其他本地文件。

## 5. JSON 写入安全

Repository 不直接覆盖正式元数据文件，而是先写入临时文件，再使用 `replace` 替换正式文件。这样能降低写入中途退出导致 `documents.json` 只写入一半的风险。

这个方式还不是并发安全方案；多个进程同时写入时仍可能相互覆盖。学习阶段 CLI 为单进程使用，后续数据库阶段由数据库事务处理并发问题。

## 6. 当前“读取文档”的范围

当前程序会访问源文件，读取其名称、扩展名、字节大小，并完整复制文件内容。它不会理解文档正文：

- 普通文本读取将在后续文档处理模块完成。
- PDF 文本提取和扫描件 OCR 在模型阶段完成。
- 文档切片和向量化在 Milvus 阶段完成。

## 7. 测试范围

- 元数据文件不存在时返回空列表。
- 添加后可由新的 Repository 实例重新读取。
- 按 ID 查询和删除。
- JSON 损坏时返回明确存储错误。
- 中文文件名和内容能够复制。
- 不存在的路径和目录会被拒绝。
- 删除时同时删除文件与元数据。
- 拒绝删除 uploads 目录之外的文件。
